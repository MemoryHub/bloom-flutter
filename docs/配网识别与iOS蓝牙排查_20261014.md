# 配网识别与 iOS 蓝牙排查（2026-10-14）

用户最终确认的流程：扫码或点击附近相框 → 建立官方 Security1 BLE 安全会话 → `bloom-setup/hello` 与云端制造身份匹配 → 进入取名 → 复用 BLE 连接让相框扫描 2.4 GHz Wi-Fi → 接收密码并实际联网 → Bloom 服务及账号绑定确认 → 首张照片。二维码解析和收到广播不能独立算“识别成功”。取名不要求相框已连接 Wi-Fi，不在取名时重新建立蓝牙会话。

本次现场：7049 能解析实屏二维码并进入取名；下一步和附近 E394 点击失败，后又出现开启蓝牙/授权提示，但用户已开启蓝牙。未取得旧版原生操作日志，不能把以下代码问题直接认定为现场唯一根因。

已确认并修正的代码问题：

- iOS 把官方 `espDeviceNotFound`（单轮扫描为空）映射为蓝牙/权限不足。现为空列表，仅依据 CoreBluetooth 的真实 poweredOff / unauthorized 状态给开蓝牙/授权提示；初始 unknown/resetting 继续等待。
- GATT 描述符可能分批、乱序返回。原来只统计当前已经发起的描述符读取，session 描述符先返回就可能过早触发安全握手，且没有一次性保护。现等待全部 characteristic 的描述符发现和读取完成，确认 session / proto-ver 可用后仅通知一次。
- 连接与重连重置 GATT 映射，忽略其他 peripheral 回调；读写请求和回调维持主线程串行。广播遗漏服务 UUID 时仍发现服务，再选择固件约定的 Bloom 服务 UUID。
- 扫描前释放前一次选择的连接；身份验证/网络扫描失败后清理连接，避免失败会话继续占用相框导致下一次无法发现。
- 两种入口都在进入取名前验证真实 BLE 身份。Wi-Fi 页面显示蓝牙重连/相框扫描的真实进度，通信、握手、网络扫描和搜索错误分别呈现。

验证：Swift 独立回归覆盖 session-first、描述符乱序、只通知一次、重新连接清空状态；Flutter 13 项覆盖身份边界、旧扫描回调隔离、失败重试、复用已验证 BLE 连接、错误提示、错误密码不绑定、密码不上传云。

原生仅保存阶段标识到 App 的 `Library/Application Support/bloom-ble-stages.log`，最多约 64KB，不保存 PoP、QR、设备 Token、密码、SSID 或包数据；官方详细日志继续关闭。真机操作后可用 devicectl 从 Bloom appDataContainer 导出此文件到本机私密排查目录。

本次仅修改 App。正式相框仍为 20261014-provision-usb-v1B / 2026101401，后端仍为 ota-provision-20261014。OTA 真实失败回滚门禁继续为 0；所有 App/云端照片保留。新机初始化仍按固件项目固定脚本执行，不为现役相框重新生成身份。

手机实装与安全 BLE / Wi-Fi 验收结果由续接记录最新条目更新，编译和模拟检查不代表真机配网已通过。

## 7051 / 固件 1402 安全分片修复

7050 真机日志已证实安全会话、身份校验和 Wi-Fi 扫描正常；用户点击连接 Wi-Fi 后通信失败。确认配网签名消息最小 517 字节，而现役固定 IDF 4.4.5 的 protocomm BLE `CHAR_VAL_LEN_MAX` / prepare buffer 为 257 字节。官方来源：https://github.com/espressif/esp-idf/blob/v4.4.5/components/protocomm/src/transports/protocomm_ble.c 。

App 7051 将大 JSON 按 100 字节 UTF-8 原始块封装，单条 JSON 不超过 240 字节；每条仍独立经过官方 Security1 加密。固件 2026101402 只接受顺序相符、同一安全会话/请求 ID 的块，15 秒超时、最大 1024 字节；完整重组后仍使用原来的服务器 RSA 签名/nonce 验证，不在中间片段写 Wi-Fi 或授权。错序/混会话/超长/非法数据均中止。配置通信失败主动断开，避免遗留会话占用相框。两端必须配套更新。

用户新增样式：添加相框页“扫描设备二维码”使用现有绿色填充按钮。用户期望占用中的相框仍可看到且禁用；现役 BLE 连接后停止广播，另一手机可能完全发现不到，因此不能把空扫描当“被占用”。云端当前 lease 区分账号，尚不能识别同账号两手机的连接占用；此产品增强未实施，现场测试先一次使用一台手机。

## 固件 1403 扫描结果竞争修复 / iOS 7052

用户确认改动前已搜索到很多 Wi-Fi，7051/1402 两次扫描报错。Mac 官方 Security1 实机探测：扫描完成、result_count=0，并非蓝牙断开。固定 Arduino 2.0.11 的 WiFiGeneric 每次 SCAN_DONE 都调用 WiFiScanClass::_scanDone，该函数无扫描归属检查即读取并清空驱动 AP 结果；IDF 配网管理器也读取同一结果，顺序竞争会令另一方取到 0。

项目新增 bloom_wifi_scan_guard.cpp，build.sh 全部构建入口使用 GNU ld --wrap=_ZN13WiFiScanClass9_scanDoneEv：仅 WIFI_SCANNING_BIT 指明 Arduino 发起时调用原实现，IDF 自己发起的扫描交给 IDF。全局 Arduino 工具链文件未修改。真实 ELF 中已确认 eventCallback 调用了 wrapper；主机回归覆盖 Arduino/IDF 两种归属。烧录仅 ota_0 应用，实物分区/稳定启动槽及旧 1402 SHA 先核验，新 Hash 已验证。

相同现场更新到 20261014-provision-scan-v3B / 2026101403 后，真实 scan_finished=true、count=7；单项 45 字节/四项 154 字节结果解析成功，证明列表可用。Mac 会话已关闭。iOS 7052 额外把真正空列表当空列表，并记录错误代码/网络数量；严格签名、主/扩展版本、覆盖安装与系统清单已核验。Android 实装仍 7051，同一分片协议兼容，无须把两端号码说成相同。用户手机 Wi-Fi 恢复与实际联网绑定继续验证，不能仅凭 Mac 扫描称开箱全部通过。

新设备脚本最低 1403 并要求扫描归属保护标记，固定流程文档已更新。
