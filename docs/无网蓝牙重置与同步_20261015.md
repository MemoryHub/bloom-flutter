# Bloom：无 Wi-Fi 蓝牙重置与服务器同步（2026-10-15）

本轮目标：手机有互联网、相框无 Wi-Fi 时仍能解绑重置；手机断网或 App 退出不会伪报完成，重新连接能继续。其次定位同公司 Wi-Fi 的 DHCP 故障。实施和实物通过分开记录，当前现场结果见文末。当前相框1519、iPhone7058已实装；Mac中继真实解绑完成，公司Wi-Fi仍未取得IP。

## 各功能的同步方式

| 环节 | 蓝牙负责什么 | 服务器与无网边界 |
|---|---|---|
| 已绑定 Wi-Fi 添加/删除 | 主人认证后在相框本地扫描、修改；取得 IP 后才保存添加 | 手机上有本地摘要；服务器以相框后续真实上报为准，不冒充实时同步；首次取得主人授权需要手机联网 |
| 无 Wi-Fi 解绑重置 | 携带服务器签名授权；相框清私人缓存、刷欢迎页、清网络；返回设备凭证 | 手机转交两阶段设备完成凭证；只有最终本地清理凭证通过，服务器才删除绑定和供图关系；账号照片不删 |
| 朝向/轮播/作息/来源保存 | 只提醒检查服务器，不传第二份参数 | 先保存服务器。BLE 不可达时保留已保存值并明确待应用；不因超时盲目回滚，避免把已被设备读取的配置覆盖回去 |
| OTA | 建云任务后提醒设备检查，取消也先登记云请求 | 下载和安装仍需相框联网；不能把 BLE 接受当安装成功；保留备用槽/签名/发布与回滚门槛 |
| 首次绑定与首播 | 扫码定位、核身份、安全配网 | 取得 IP 后由原配对和首播机制完成；实际刷完才报首播完成，后台可恢复 |
| 普通浏览/自动轮播 | 浏览不自动连接 BLE | 原定时、选图、缓存、每轮读服务器参数不变 |

服务器仍是展示参数唯一权威。蓝牙常驻需要 ESP32 轻睡而非真正深睡；底层等待方式与每轮业务流程分别描述，不能声称深睡中保持 BLE。

## 无网重置事务

1. 手机先创建/复用云 reset 任务；没有手机互联网时，不下发破坏性清理。
2. 手机通过 Security1、真实设备 ID 和 P256 主人认证取得设备新 nonce，服务器原子地检查主人、任务、OTA 互斥并签发绑定 nonce/设备/任务/代次的授权。状态进入 running / ble_reset；授权已发出后不提供盲目取消，防止迟到授权执行。
3. 相框仅在主循环执行清理和欢迎页刷新。独立 NVS 日志记录阶段，不改制造身份结构、bootloader、分区或 eFuse；重启恢复先处理重置，禁止私人旧照片重新显示。
4. 相框实际欢迎页完成、清网络成功后，生成任务绑定的 physical_complete 凭证。凭证使用设备 Token 的摘要作 HMAC 密钥，Token 和摘要均不经过 BLE；手机只转交凭证，不能凭布尔值伪造完成。
5. 手机将凭证交给服务器，服务器核验后保留主人、任务置 ble_commit，返回签名确认。相框验证签名后撤销本地主人授权、清主人标志，保存 local_committed 检查点。
6. 手机转交第二份 local_committed 凭证，服务器才在同一事务移除主人、供图关系、邀请、旧计划及设备私人设置。云照片、制造身份及专属二维码保留。接口重复提交幂等；旧任务不能删除后来重新绑定的新主人。
7. 相框保留任务与凭证检查点，等待几秒供手机读取后重启。手机断网、BLE 断开、App 被杀或回报丢失时重新连接同一任务继续；已持久保存的欢迎页检查点不会重复刷新。

## 中断时的状态

- 授权前手机断网：相框不清理，原绑定和照片保留。
- 授权后 BLE 未送达：云任务保留为待继续，不假报已清理，可重新连接并重新签发当前 nonce 授权。
- 清理后手机断网：相框锁在重置事务，保留设备凭证和恢复入口；服务器保留绑定，页面提示重新连接继续。
- 服务器确认后 BLE 断开：同一任务可重取确认；相框不会接受新设置/配网绕过未完成的重置。
- 相框本地清理已完成、最终 HTTP 丢失：设备保存最终凭证；原主人重新连接转交，接口幂等完成。
- 执行中不回滚清理结果、不强行取消，不把“返回页面”当作取消。

实际故障恢复：在physical_complete / stage3断开BLE，服务器仍owned=true / ble_reset；重新连接完成云确认和本地主人清理，到stage5再次断开，服务器仍owned=true / ble_commit。设备实际重启后，第三次连接仍可读取持久最终凭证；转交后服务器才移除主人。重复finish接口幂等，照片摘要不变。首轮诊断脚本在提交/最终步骤后的admin_end收到session_expired，这是恢复连接没有旧主人认证的预期结果，App原_release已捕获该异常并断开；修正诊断脚本的收尾处理后幂等finish重跑成功，不因此更改固件。

三类验证需分开：主机测试覆盖手机断网/HTTP回包丢失；真实设备覆盖分阶段主动断开BLE、重连、重启后恢复；未实测强杀iPhone进程、手机真正断网或执行中物理拔电。

## 首次已有图库的播放按钮与日常管理的区别

已有图库时按钮为“完成并开始播放”。当前FramePlaybackController只向服务器POST first-playback任务并观察真实进度，没有额外BLE检查调用。刚绑定完成、仍在等首次播放的相框保持维护联网，约5秒检查一次云任务，再走原计划/RAW下载/真实波形/完成回报；不是等待下个常规15分钟时段。网络/RAW/面板仍会耗时，不能承诺点击即刻完成。若此时相框Wi-Fi断开，首播无法完成；不是通过BLE发送照片或绕过服务器参数。

欢迎页重置时实际刷回一次；完成持久检查点后的重连/重启不会重复刷欢迎页。未绑定、未完成首播时保持欢迎图，准备好的照片进入真实波形后才替换。日常浏览/列表轮询不自动连接BLE；后台自动轮播依然不依赖手机在旁。

## 公司Wi-Fi新增证据与停刷边界

同名网络下Mac当前实际是5GHz channel36/802.11ac/WPA2，ESP32-S3是2.4GHz channel6/WPA-WPA2混合；不能据三台客户端可上网就说它们与相框走同一无线接入链路，也不能据相框失败就归罪路由器。

独立无BLE应用使用WiFi.persistent(false)、WIFI_STORAGE_RAM、原Arduino2.0.11，仅临时写应用，不写制造身份、业务NVS或已存网络。原始测试45秒关联但无IP。第二次只统计面向本机的802.11帧元数据、不保存帧负载：监听接口全部返回0，44秒时ACK27、面向本机数据2（从连接初期后没有增加）、protected0、bad0、目标AP组播0；同样无IP。该统计不是完整AP/DHCP抓包，不能证明DHCP服务未收到请求或未发OFFER。诊断已结束并恢复1519，真实v18启动核验通过；没有关Wi-Fi省电、换网络、改静态IP/MAC或升SDK。仍缺能观察到同一次DHCP交互的网络侧证据，当前没有确认根因，禁止宣称已修好。

重置前16MB备份中的state_v4通过NVS chunk CRC及完整Bloom CRC验证：plan287、screen11864、next11865、下次2026-10-15 08:45、最后校时08:40:05、计划有效到当日23:59、failStreak35。实际冷启动日志epoch_ms=0，生产bloomEarlyPush遇无有效时钟会保留原图，不靠手机时间/旧计划猜当前时刻。证明当前冷启动且无网时不能按绝对时刻刷缓存；尚未还原最初停刷瞬间，因此原始停刷根因仍待完成，不能简单归为缓存损坏或计划已过期。原计划/显示业务核心没有因本轮更改。
